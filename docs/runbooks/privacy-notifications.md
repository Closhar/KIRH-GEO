# Геособытия, уведомления и приватность

## Задания

- `geo:process-outbox --limit=100`: выполнять постоянно или scheduler; обрабатывает только geo/SOS/consent/membership события, не забирает billing outbox. Отдельные consumer receipts, повторяемые записи, повторная проверка согласий. Также завершает истёкшие live-сессии и списывает фактические округлённые минуты из резервов.
- `geo:maintain-locations --limit=10000`: минимум ежедневно. Создаёт будущие UTC-партиции и уменьшает audience expiry по текущим лимитам. Удаляет ограниченное количество истёкших audience/points. При backlog запускать чаще до очистки; размер и lag мониторить. Никогда не использует `DROP CASCADE`.
- `geo:process-privacy --limit=10`: экспорт и удаление, возобновление после сбоя. `--replay-tombstones` обязателен после восстановления backup до открытия пользовательского трафика.

Maintenance-роли должны иметь право создавать партиции. Runtime API не должен владеть таблицами. Export-файлы находятся на private local disk, не в public/storage; файловая система/резервные копии должны быть зашифрованы. URL скачивания требует действующую сессию именно субъекта, не является публичной capability. Экспорт истекает через 24 часа. Объём экспорта может быть большим, мониторить место и продолжительность job.

## WebSocket и push

`PrivateChannel(users.{uuid})` переносит только `{type,event_id}`. Клиент получает сигнал обновления и запрашивает координаты через авторизованный API. По `access.changed` очищает локальную карту и заново получает разрешённые данные. Согласия заново проверяются перед выдачей REST и перед внешней доставкой. Уже отображённые получателю данные нельзя отозвать с его скриншотов.

FCM: секретный JSON service account задаётся `FCM_CREDENTIALS_PATH`; адаптер обменивает подписанный JWT на кратковременный OAuth-токен и использует HTTP v1. APNs: certificate-based authentication, `APNS_CERTIFICATE_PATH`, `APNS_KEY_PATH`, `APNS_KEY_PASSWORD`, `APNS_TOPIC`, `APNS_SANDBOX`. Нужны HTTP/2-enabled curl/Guzzle и правильный production/sandbox сертификат. Секреты не хранить в Git или application_settings.

Отсутствие credentials не выдаётся за доставку: попытка остаётся pending с backoff, затем failed после восьми попыток. Логи содержат только ID операции и класс ошибки. Push содержит общее уведомление и opaque event ID без координат, имени или маршрута. Подтверждение провайдера означает принятие сообщения провайдером, а не показ на устройстве. При сбое после отправки до фиксации БД возможна повторная доставка; клиент дедуплицирует event ID. Несколько устройств могут получить повторное сообщение при частичном сбое доставки; collapse ID уменьшает повторения, но не обещает exactly-once.

До production нужны тесты на реальных iOS/Android, credentials, delivery/error monitoring и ручной retry failed записей после устранения причины. Автоматическое удаление невалидных device tokens пока не выполняется: delivery остаётся доступной для диагностики без записи секретного токена в лог.

Основания интеграции: [Firebase HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api), [APNs requests](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns).

## Удаление

Запрос подтверждается пользователем. Для рабочего пространства с другими участниками сначала передаётся ownership. Перед удалением billing owner требуется отключить автопродление; передача ownership сама по себе не переносит платёжные обязательства. Сразу закрываются согласия и сессии. Worker удаляет GPS, точки маршрутов, личные геозоны, push tokens, exports, activity records и идентификаторы профиля. Неуспешная очистка Redis не считается завершённым физическим удалением.

UUID-запись пользователя остаётся обезличенной ради целостности FK. Финансовые записи, consent/audit и связанные доказательные записи не объявляются удалёнными: response перечисляет исключения. Конкретные законные сроки и процедура обезличивания этих записей требуют настройки оператором до коммерческого запуска. Обычные логи не должны содержать координаты/секреты, поэтому отдельной очистки такого содержимого не предусмотрено.

Tombstone хранит HMAC пользовательского UUID. Сейчас его ключ — APP_KEY: при ротации ключа необходимо отдельно сохранить возможность проверки старых tombstones. После backup restore импортировать актуальный журнал tombstones из независимого защищённого backup и выполнить replay до запуска API. Сам backup восстанавливает состояние прошлого; без актуального журнала обещать отсутствие возвращённых данных нельзя.
