# Billing implementation and activation

Authenticated routes are in `routes.php`; verified provider callbacks are in `webhooks.php` and must be registered outside device authentication. All workspace writes require `billing.manage`, then a workspace lock, then idempotency receipt validation. Feature grants/revocations go through EntitlementService. Provider callbacks do not require a member login; they require independent provider authenticity checks and match registered payment amount/currency.

Implemented: published catalog, monthly/yearly calendar periods, trial with billing-owner reuse protection, free access/discount/free months promotions, hosted checkout, verified settlement/refund callbacks, invoices, entitlement update, immutable audit/outbox, partner accrual/reversal. Promotion redemption supports one benefit per code and new_customers_only eligibility. Redeem a discount before creating checkout; its cycle/budget is reserved at checkout creation, including subsequently abandoned checkout. Discounts do not stack; earliest active discount applies. Use free_access instead of a zero-price checkout. A free-month benefit requires an active subscription. Trial settings come from application_settings namespace billing: trial_plan_id and trial_days; zero disables trials.

Checkout defaults to prepaid. Explicit `auto_renew=true` requires BILLING_RENEWALS_ENABLED and customer opt-in; only a payment-method ID returned by authoritative verification can authorize renewal. `billing:renew` runs every minute, uses a deterministic key per subscription period, retains the purchased price version and creates one pending charge. Access extends only after verified settlement. Cancellation disables future charges while preserving the paid period. Failed renewal becomes past_due; automatic dunning retries and grace extensions are not yet enabled. Cancellation after a renewal request was sent cannot retract that in-flight payment and needs refund handling if requested.

`billing:reconcile` retrieves pending YooKassa payments older than two minutes and recovers missed settlement/cancellation callbacks; schedule every five minutes without overlapping. Refund polling and automatic dunning remain release work. Store purchase restore and refund initiation also remain release work. StorePurchaseProvider/VerifiedStoreSubscription define the verification boundary; unconfigured provider fails closed. Apple/Google config contains application identifiers, but no adapter pretends to verify a purchase without credentials. Entitlement expiry is checked on every resolve. A pending checkout needs settlement/cancellation confirmation before creating another checkout.

## Providers

- Sandbox: local/testing only, disabled by default. Set BILLING_SANDBOX_ENABLED and a random BILLING_SANDBOX_WEBHOOK_SECRET of at least 32 characters. Callbacks require X-Billing-Timestamp (Unix seconds, ±300 seconds) and X-Billing-Signature = HMAC-SHA256(timestamp + '.' + raw JSON, secret). Checkout URL uses reserved sandbox.invalid; no real payment occurs.
- YooKassa: disabled by default. Required YOOKASSA_ENABLED, YOOKASSA_SHOP_ID, YOOKASSA_SECRET, YOOKASSA_RETURN_URL (HTTPS). Incoming webhook body is an untrusted hint; adapter retrieves payment/refund from the fixed authenticated provider API and uses its values. Merchant activation, fiscal receipt configuration, contract, credentials and sandbox acceptance are external release dependencies. Adapter supports hosted checkout, opt-in saved-method renewal, and payment/refund notifications. Method references are never returned to mobile clients.

Reference: [YooKassa webhook documentation](https://yookassa.ru/developers/using-api/webhooks), [saved-method recurring payments](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/pay-with-saved), [API reference](https://yookassa.ru/developers/api).

Callback normalization and billing mutation currently run synchronously in one database transaction; callback receives HTTP 200 only after commit. Inbox stores encrypted normalized facts, not raw callback bodies. On a failure the transaction rolls back and callback remains unacknowledged for provider retry. Moving durable inbox processing into dedicated workers is an outstanding scaling step. Duplicate normalized event IDs produce no second payment, invoice, entitlement grant, refund or commission. Late cancel/success cannot roll back terminal states. An early refund before settlement returns a retryable conflict.
